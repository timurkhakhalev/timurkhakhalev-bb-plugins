# Native BB performance check — 2026-10-29

Verified the APNG loader/shimmer change inside `/Applications/bb.app`, version 0.48.0, Electron 44.9.3 / Chromium 152.0.7977.167. Used native clicks and keystrokes, with DevTools closed during measurements. No app restart or page reload.

## Loader comparison

The same window and expanded sidebar were kept for all three conditions. Added a temporary pending-row fixture to the existing timeline so the animation stayed visible without starting an agent or modifying a conversation. It used the plugin's normal pending-row selectors and the selected `dots` loader. The enabled builds each had 5,068 DOM elements.

Renderer PID 34012 CPU time was sampled over three 10-second windows per condition using `ps`. This measures the whole renderer, not just its main thread; another thread was active in the sidebar, so background activity contributes noise.

| Condition | Samples, CPU ms/s | Median |
|---|---|---:|
| Plugin disabled | 67, 67, 120 | 67 |
| Original CSS animations | 500, 499, 501 | 500 |
| APNG masks | 79, 142, 137 | 137 |

The observed median fell by 73%. Original bundle `239487d3c54776ac` exposed `bui-px-a/b/c/d` and `bui-shimmer-text` animations. Fixed bundle `d11caad28a2912ac` had an APNG mask and no active CSS animations in the same fixture. The fixture was removed afterward. This is a controlled animation check, not a full live streaming benchmark.

## Round 2: coins, remaining loops, observers (Chrome 156 investigation)

Measured in an isolated Chrome 156 profile on the same server and thread. The sidebar's Inactive shelf was expanded (~8.4k elements). The plugin was injected from the built `dist/app.css` plus its content-script modules, and the served copy was disabled for the run. A real `Running…` row from a live agent turn was visible. Native follow-up is recorded below.

- **coins**: the paint worklet was driven by an `@property` keyframe, so it restyled and repainted every frame. Idle main-thread time was 348 ms/s at 180 commits/s, against 20 ms/s with the plugin off. It is now a 105-frame APNG mask: 5.236 s, half the original 10.472 s cycle, which repeats after half a ring turn. It is rendered by `scripts/loader-apng.py` from the worklet's geometry, and alpha is quantized to 16 levels. Idle cost is 11–21 ms/s at 1 commit/s. Compared with a canvas render of the worklet code at 2×, mean alpha error is ~4/255. `coins-worklet.ts` and the `data-bui-coins-ready` handshake are gone.
- **No looping CSS animation is left in app.css or the composer CSS.** What remains is one-shot: approval-card fade, tooltip and picker transitions, and the 220 ms composer height FLIP. `check-loader-apng.py` now fails if `app.css` declares an `infinite` animation.
- **Phase sync**: two elements with the same APNG mask, mounted 1.3 s apart, showed identical frames in three screenshots. The masks share one clock, so remounted rows don't restart. `phase-sync.ts` stays for BB's own CSS spinners.
- **Reduced motion**: with `prefers-reduced-motion: reduce` emulated, every loader uses a still mask (drive/orbit grid, dots grid, coins frame 0), and so does the child-thread orbit, which used to keep animating. The label falls back to BB's own reduced-motion style. No CSS animations run.
- **Observers and forced layout**: six thread switches plus 5 s idle were CPU-profiled. Plugin JS totalled 24 ms, mostly the `perf-markers` rAF scan, against ~2.9 s of page JS. The plugin forced 4 style recalcs totalling 0.1 ms (`spatial-tooltip` sync). No change was needed.
- **CSS size**: the masks are declared once as `--bui-mask-*` on `:root`. The build's `-webkit-` prefixing would otherwise duplicate every data URL. This brought built `app.css` from 204 KB to 120 KB. A forced full recalc measured 146–150 ms vs 149–159 ms with inline URLs, so no regression.

- Six native thread switches with Inactive collapsed recorded click durations 48, 48, 40, 40, 48, 40 ms. The observation interval contained 12 long tasks, total 1,701 ms, maximum 216 ms. - APNG validation passed all eight embedded assets after the rerun.

Final state: plugin enabled, loader dots, exact bundle `124144e776d56b41`, reduced-motion emulation off, DevTools closed, optimization thread selected and Inactive collapsed. ## Round 3: residual renderer cost of the APNG masks (standalone Electron 44.9.3, not bb.app)

Native round 2 left final dots at a 124 ms/s renderer median against 78 disabled. To attribute the gap without touching the user's window, I ran the same Electron/Chromium build (44.9.3 / 152.0.7977.167) as a standalone app. Its window was near-transparent and ignored input. It loaded the same server page, with the served timur-ui sheet toggled in-page and one real pending row from this thread's running tool call. A frame probe confirmed rendering wasn't throttled (161 commits/s with a CSS loop). This is the same engine but not the bb.app shell, so it doesn't stand in for a native check.

- **Where the cost is.** Per-thread trace, 6 s windows: main-thread work is small (one main frame per second, no style recalc from the masks). The extra cost sits on the compositor thread and raster workers. Each animated mask is an independent image clock, and every tick schedules an impl-side invalidation, a draw, and re-raster of that layer. Draws/s were 21 with the plugin off (BB's own shine, 30 fps), 36 with the served 40 fps sweep plus dots, 46 with the dots loader plus BB's shine, and 33 with only the sweep animating. Observers and JS aren't involved.
- **Controlled fixture.** 500 rows plus one pending row, same masks, interleaved 8 s renderer-CPU windows, 3 each. Each window is shown as ms/s.

  | Variant | ms/s |
  |---|---|
  | BB shine alone | 8–16 |
  | Our sweep at 40 fps | 26–28 |
  | Sweep at 30 fps | 11–13 |
  | Sweep at 20 fps | 8–12 |
  | 30 fps dots alone | 11–13 |
  | 30 fps dots + 30 fps sweep | 21–26 |
  | 40 fps dots + 40 fps sweep | 22–33 |

  Adding the dots loader to the 40 fps sweep (27–30) cost no more than the sweep alone. `will-change: transform` on the loader made no difference.
- **Not applied.** A ~30 fps variant of drive/dots/orbit/sweep was built and staged, then dropped at the owner's request to keep the 40 fps motion. The shipped masks are byte-identical to the round-2 (fix2) masks; `loader-apng.py` keeps `FRAME_MS = 25`.
- **On the real page** (4 interleaved 10 s windows): served 40 fps 31–58 ms/s, 30 fps 19–48, plugin off 13–30. Background activity from the live page is too noisy to quantify this delta. Only the fixture isolates it.
- **What remains by design.** The loader and the label sweep are two separate animated images, so they tick on two clocks where BB alone ticks on one. Setting `shimmer` to off makes the label use BB's own shine and removes one clock. Rendering the loader with BB's own icon (`loader: bb`) removes the other. Both are user choices; nothing was changed by default.
